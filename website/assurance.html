Assurance

What Pollis checks about its own code, and what those checks found.

Four things run on this codebase: an independent rebuild of every release, machine-checked proofs of the code where a bug would lose messages, a dependency policy enforced on every pull request, and signing keys with documented custody. They have run for months; this page publishes their results, with links to the machine-generated records.

The artifacts page covers the transparency log and the commands that check a download.

1 · Independent rebuild of every release

After each release, a workflow rebuilds the Linux AppImage payload from the public source at that tag, on a clean runner, and asserts that the hash it gets is the hash already recorded in the public transparency log. It uses no Pollis secrets, so anyone can fork it and run the same check, and it trusts one pinned ML-DSA-44 key.

Where this guarantee ends

It covers the Linux AppImage payload. The .deb, .rpm, macOS and Windows builds are covered by published-bytes-match and build provenance.

Reproduction needs the published build recipe as well as the source, because one build-time value is compiled in. Without the recipe a third party can still prove log inclusion, but not bit-for-bit reproduction.

Reading the table. The rebuild runs only when the release workflow succeeds, so a release whose workflow did not finish has no verdict and is marked never checked. An AppImage bundles system libraries copied from the build machine, so a rebuild is only comparable on the same CI machine image as the release. The workflow compares the machine image the release recorded with its own and reports one of did not reproduce, build environment drifted or no recorded recipe. All three fail, since an inconclusive rebuild is not a pass; only the first is a claim about the shipped binary. Every run is kept: a re-check adds a run rather than replacing one, and each row shows its release's latest run with a count of earlier attempts.

2 · Machine-checked correctness

Pollis promises that messages work: delivery to every current member, decryption, offline and online cycles, reconnects. Where that promise can break is in a few small, pure decision functions: when a delivery cursor may advance, when a commit may be accepted at an epoch, when old data may be deleted. Those are checked by machine.

TLA+ — the design

TLC checks two specifications on every relevant pull request, enumerating every reachable state of each model.

Measured on a run of scripts/tlc-check.sh against TLC v1.8.0.

A passing check means nothing if the invariant can no longer fail, so three deliberately broken variants run alongside and each must produce a counterexample. Dropping the commit-log head guard violates OnePerEpoch; dropping the migration compare-and-swap violates OpeningClosesTheHead; guarding retention on the fastest member rather than the slowest violates NoLossForCurrentMember. If any of those ever passes cleanly, the gate fails.

Kani — the actual Rust

TLA+ checks the design, not the shipped code. 35 Kani harnesses (19 proofs, 16 teeth) run bounded model checking over the real Rust functions: the delivery watermark, the rejoin gate that keeps a revoked device out of the tree, own-commit canonicalization, gap detection, the Delivery Service's head arithmetic, and the retention floor. Sixteen of the proofs are paired with a mutant that Kani must refute, such as an off-by-one in the watermark, a fail-open rejoin gate, or a retention floor that adds slack instead of subtracting it.

Every run publishes a summary and a downloadable artifact: TLA+ runs · Kani runs · design doc · the specs themselves.

Where this guarantee ends

Both are bounded. TLC checks a small model (three clients, a few epochs) and Kani checks small input domains. A bug that only appears at larger scale is outside both. Exhaustive over a small space is stronger than sampling a large one, but it is not a proof about the running system.

They cover the decision functions, not the program. The proofs range over pure functions extracted for the purpose. Database calls, the network, the MLS library and the UI are covered by ordinary tests and a weekly fuzzing soak, not by proofs.

One invariant has no machine-checked proof: that the test schema equals the production schema. A mechanical equality check enforces it instead, as the design doc notes.

3 · Supply chain

Pollis's Rust lockfile resolves to 1,024 crates. Two gates run on every pull request and every push to main that touches a manifest, the lockfile or the policy, and weekly on a schedule, both against pinned tool versions (cargo-deny 0.19.9, cargo-vet 0.10.2) so the gate itself does not drift.

cargo-deny — advisories, licences, sources

  • Advisories. Any RustSec advisory against the graph fails the build unless it has an exemption naming its RUSTSEC- id with a written reason; there is no blanket suppression. The check runs on every change to the dependencies and weekly on a schedule.
  • Licences. An allow-list of 17 identifiers, each one actually present in the graph. MPL-2.0 is permitted with the reasoning written down (file-level copyleft, no reach across a module boundary).
  • Sources. crates.io only, plus exactly one git dependency: an openmls commit, needed for the post-quantum MLS ciphersuite that no published release carries yet. The revision is pinned in Cargo.toml, so it cannot follow upstream main.

cargo-vet — review provenance

cargo-vet records who has reviewed each crate version. Pollis imports 509 audits from six organisations that publish theirs: Mozilla (212), Google (115), Bytecode Alliance (72), ISRG (55), Zcash (42) and Embark (13). Another 31 crates are trusted by publisher identity. The rest sit in an exemption baseline.

Read the policy directly: deny.toml · supply-chain/ · gate runs.

4 · Signing keys, custody and rotation

Every claim on the artifacts page reduces to two pinned ML-DSA-44 keys: the log signing key, key id 6cbd4b2aed5c4bf1, and the offline root that can authorise its successors. This section covers who holds it and what happens if it is stolen.

KeySignsCustody
Transparency-log signing key
ML-DSA-44		 Signed tree heads for all three logs A GitHub Actions secret, backed up in a secrets manager
Offline root key
ML-DSA-44		 Nothing but key-set statements: "these keys may sign these logs, until this date" Offline. Not in CI, the secrets manager or the repository
Release code-signing macOS (Apple Developer ID) and Windows (Azure Trusted Signing) installers GitHub Actions secrets
Sigstore identity cosign signatures and SLSA provenance No held key: a short-lived certificate bound to the release workflow's OIDC identity

The key has been rotated once. In August 2026 the log signing key was replaced with fresh material and all three trees were republished from source data under new domain-separation contexts. The result was verified from a machine that had not performed the rotation.

A compromised signing key may need a new build. Clients also trust signers named in a key set authorised by the offline root, and a signer that only the key set names can be dropped by publishing a new key set, with no client update. Today's signing key is also compiled into the app and the verifier, and a key set cannot revoke a compiled key, so retiring it needs a client release. The runbook drops a compromised key outright rather than giving it a short expiry, since an attacker who can delay a client's fetch keeps the key alive that long. It also says to act on suspicion, without waiting for proof.

The pinned key is copied into the Rust core, the verifier, this website, two workflows, the key-set statement and several documents. CI checks that the copies agree on every pull request (scripts/check-pinned-log-key.py), and a separate workflow checks that the deployed site pins the same key. The verifier is released so a third party can audit the logs without asking us for anything.

5 · Security reviews

Pollis has had two full adversarial security reviews, in September 2026, both by teams of AI agents working read-only in parallel, each required to cite the source line behind every finding. Every finding was addressed, and each fix ships with a regression test confirmed to fail against the pre-fix code.

6 · Operations

Live service status, running version and daily uptime are published at status.pollis.com. The continuity plan, including how to tell a stalled transparency log from a withheld one, is on continuity. Legal demands for user data are on legal requests.

Reporting a vulnerability

Report privately through a GitHub security advisory, not a public issue. The machine-readable policy is at /.well-known/security.txt and the terms are in the disclosure policy.

Pollis is source-available, not open source: PolyForm Noncommercial 1.0.0. You may read, build, audit and modify it for noncommercial purposes; commercial use needs a separate licence. Auditing the code and publishing what you find is permitted.
