Bots for developers

Post alerts into a channel, how the bot runtime decides what happens, and writing your own App.

Each bot's runtime, pollis-bot, listens for alerts on a small HTTP endpoint on its own machine. It encrypts each alert and posts it into the bot's group as the bot.

Setting up a bot first: Bots and Self-hosting a bot.

The alerts webhook

Turn it on with pollis-bot run --webhook, or in config.json:

{ "webhook": { "bind": "127.0.0.1:8787" } }

The first start with the webhook on prints each installation's secret once (pbw_…). Lost it? pollis-bot rotate-secret --installation <id> prints a new one; restart pollis-bot run to use it. The installation id is the first column of pollis-bot status.

POST http://<bind address>/hooks/<installation id> Content-Type: application/json {"channel": "alerts", "text": "disk 91% on db-1"}
  • channel: a text channel of the bot's group, by name (with or without #, any case) or by id.
  • text: up to 4,000 characters.
  • The listener binds to 127.0.0.1:8787 by default. To take alerts from another machine on your network, set bind to that interface's address; callers still need the secret. It speaks plain HTTP, so keep it on networks you trust or put a TLS reverse proxy in front.

Authenticate and send

HeaderValue
AuthorizationBearer <secret>
X-Pollis-Signature sha256=<hex HMAC-SHA256 of the raw body, keyed with the secret>

Use one. A request carrying a signature must have a correct one; a bearer header cannot make up for it.

SECRET='pbw_…' URL="http://127.0.0.1:8787/hooks/<installation id>" curl -sS -X POST "$URL" \ -H "Authorization: Bearer $SECRET" \ -H "Content-Type: application/json" \ -d '{"channel": "alerts", "text": "disk 91% on db-1"}' BODY='{"channel": "alerts", "text": "deploy finished"}' SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" | sed 's/^.* //') curl -sS -X POST "$URL" \ -H "X-Pollis-Signature: sha256=$SIG" \ -H "Content-Type: application/json" \ --data-binary "$BODY"

On the bot's machine, pollis-bot post sends through the running webhook for you, signed with the installation's secret:

pollis-bot post --installation <id> --channel alerts "backup finished"

Several hosts: send the same alert to each of a bot's hosts with the same X-Pollis-Delivery header (1 to 128 characters of A-Z a-z 0-9 . _ : -), and exactly one host posts it; the others answer claimed_elsewhere.

Rate limit, per installation: a burst of 10, refilled at 30 a minute (webhook.burst, webhook.per_minute). Over it: 429 with Retry-After, and nothing is posted.

How a job runs

Every trigger goes through the same seven steps:

  1. Trigger. Something arrives for an installation: new messages in the group may be waiting, or a webhook call comes in.
  2. Lock. One job per installation at a time; installations run in parallel.
  3. Catch up. The bot's view of the group is brought up to date through the normal message path. New messages become message triggers, oldest first; the bot's own never do.
  4. Handle. The installation's handler returns a list of actions. It holds no keys, opens no connections and sends nothing itself.
  5. Claim. If there are actions, the host claims the trigger on the Delivery Service. If another host of the bot claimed it first, this host drops its actions.
  6. Check and apply. Each action is checked against the installation's grants; what passes is sent through the normal send path, what doesn't is reported and never sent.
  7. Unlock.

There are no timers: a job starts when the runtime starts, when a realtime event says the group may have changed, or when a webhook call arrives.

Triggers, claims and grants

TriggerTrigger key
A new message in the bot's groupmsg:<envelope id>
A webhook callhook:<delivery id>

Why only one host acts. A bot with several hosts sees every message on each of them. Before acting, a host claims (installation id, trigger key) on the Delivery Service, which keeps it under a uniqueness constraint: the first claim wins, the others discard their actions, and the winner's own retry wins again. A trigger with no actions is never claimed.

Retries never double-post. If the claim or the send cannot reach the Delivery Service, the job stops at that message and retries it, in order, on the next wake-up. The message it posts has an id derived from the installation, the trigger key and the action's position, so a retry re-sends the same message.

Grants. Every action is checked against what the installation is allowed to do. Today that is post to the text channels of the bot's own group; anything else is refused.

The full write-up is in docs/bots/concepts-for-developers.md and docs/bots/alerts-webhook.md, which this page is kept in step with.

Write an App in TypeScript

An App is the code that decides what a bot does. You write it in TypeScript with @pollis/app; the group's own runtime runs it in a sandbox, where it can do only what its manifest asks for and an admin allows. You never run the bot or hold its keys.

import { app } from "@pollis/app"; export default app({ manifest: { read: { channels: ["*"] }, actions: ["reply"] }, async onCommand(cmd, ctx) { await ctx.reply(cmd.message, `Hello, ${cmd.args || cmd.message.author.displayName}!`); }, });
  • pollis app new hello-bot --lang ts creates an App with one handler, a test and a README.
  • pollis app test runs your tests against the built App in the same sandbox the runtime uses, offline: a call the manifest does not allow fails in a test exactly as it would in a group.
  • pollis app build writes the component and pollis-app.json and prints the App hash. The same source and lockfile give the same hash on any machine.

The manifest is the contract. It lives in your code and is written out at build, so it cannot drift: the channels the App reads, what it may do (reply, post, react, editing or deleting its own messages), how much state it keeps, and the exact hosts ctx.fetch may reach. With no hosts listed, the App cannot send anything outside the group.

Limits. An App can send what it reads to the hosts its manifest lists. It has no files, sockets or processes, so Node built-ins such as fs, net and child_process are refused at build with the reason; plain-JavaScript npm packages work. It sees attachments' names, types and sizes, not their bytes. Every job starts fresh, within 10 seconds and 64 MiB, and nothing it queued is applied unless it finishes without an error. No App can moderate.

The walkthrough, from an empty folder to a tested App, is docs/bots/developer-guide.md; every function and limit is in docs/bots/app-reference.md.
