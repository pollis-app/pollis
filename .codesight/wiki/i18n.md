# Localization (i18n)

How the React renderer gets its user-facing copy, where the language
preference lives, and what a follow-up locale actually has to touch.

Working checklist for adding a locale: [`frontend/src/i18n/README.md`](../../frontend/src/i18n/README.md).
This article is the design record.

## Stack

`i18next` + `react-i18next`, initialized once in `frontend/src/i18n/index.ts`
and mounted as an `I18nextProvider` in `main.tsx`, outside `ErrorBoundary` and
`QueryClientProvider` so even the crash screen can be translated.

| File | Role |
|------|------|
| `frontend/src/i18n/index.ts` | i18next init, `setLanguage`, `adoptUserLanguage`, `<html lang/dir>` sync |
| `frontend/src/i18n/languages.ts` | `SUPPORTED_LANGUAGES`, tag normalization, OS-locale resolution |
| `frontend/src/i18n/namespaces.ts` | The namespace list; `common` is the default |
| `frontend/src/i18n/storage.ts` | Device-local `localStorage` persistence |
| `frontend/src/i18n/resources.ts` | Eager `import.meta.glob` of every catalogue |
| `frontend/src/i18n/locales/<lng>/<ns>.json` | The catalogues |
| `frontend/src/components/Preferences/LanguageSection.tsx` | The picker |

## Shipped locales

| Code | Endonym | `dir` | Notes |
|------|---------|-------|-------|
| `en` | English | ltr | Source catalogue and `fallbackLng`. Every key originates here. |
| `ru` | Русский | ltr | Machine-translated, pending native review. All 38 plural families carry the full Russian `_one`/`_few`/`_many`/`_other` set. |

`en` is the only catalogue a new key may be *authored* in; every other locale
is a translation of it, so "what is still untranslated" stays a diff against
`en` rather than a hunt through the source.

A change may therefore land **English-only**, and normally should: writing six
machine translations by hand alongside the feature is how a catalogue fills up
with confident nonsense. `i18n-check` reports the shortfall as a warning (see
[Tests](#tests)) and a later pass clears it.

## Namespaces

One JSON file per feature area, not one flat catalogue: a translator working
on voice should never have to read the settings copy.

`common` (shared verbs/nouns), `auth`, `nav`, `chat`, `channels`, `dms`,
`voice`, `settings`, `search`, `emoji`, `saved`, `errors`, `arcade`.

Keys are addressed `namespace:section.item` and are **stable identifiers, never
the English text** — so a copy edit stays a copy edit instead of orphaning
every translation of that string.

## Where the language preference lives, and why

**Device-local `localStorage`**, keyed by user id, mirroring the device-local
font size (`loadDeviceFontSize` in `utils/colorUtils.ts`). It is *not* in the
synced preferences blob.

Two reasons, one of which is decisive:

1. Language is an OS-level property of the machine, like the keyboard layout.
   A shared office machine in one language and a personal laptop in another is
   a real configuration that syncing would break.
2. **Decisive:** the synced blob is read through `get_preferences`, which needs
   a signed-in user *and* an unlocked local DB. The login, PIN-entry and
   enrollment screens have neither. A synced-only preference therefore could
   not localize the first screens a non-English reader ever sees — which is
   most of the point of the feature.

Saving for a signed-in user also writes a device-wide entry, so the next
pre-auth boot speaks the language this machine last chose rather than falling
back to the OS guess. `adoptUserLanguage`, called from `completeSignIn` in
`App.tsx`, re-resolves to the signing-in user's own choice before the shell
renders.

## First-run default

`resolveInitialLanguage()`:

1. the stored device choice, if any;
2. otherwise the first entry of `navigator.languages` we ship a catalogue for
   — under Tauri the webview inherits the OS locale, so this is the OS's
   answer, and under the Playwright browser tier it is whatever the test sets;
3. otherwise English.

Region subtags degrade to the base language (`pt-BR` → `pt` when `pt` ships),
because a user should land on the language they read rather than dropping all
the way to English over a missing regional catalogue.

**Registered codes are base tags — the degrade rule is also a constraint on
what a locale may call itself.** `normalizeLanguage` splits on the first
separator and matches the base, so a `zh-Hans` entry could only ever be
selected by an OS reporting exactly that tag, which no real one does (`zh-CN`,
`zh-Hans-CN` both reduce to `zh`). Casing rules it out from the other side too:
`normalizeLanguage` lowercases every tag, while i18next canonicalizes through
`Intl.getCanonicalLocales` before checking `supportedLngs`, so `zh-hans` fails
i18next's check and `zh-Hans` fails ours — and the failure mode is a silent
fall back to English, not an error. Simplified Chinese therefore ships as `zh`,
with `简体中文` as the endonym carrying the script distinction. Shipping a
second script for one language would mean reworking `normalizeLanguage`, not
adding a subtagged entry.

## Fallback

`fallbackLng: "en"`, `returnEmptyString: false`. A key missing from the active
language, or present but left as `""` in a half-finished catalogue, renders the
**English** string rather than a raw key. Partial translations are always
shippable, and a locale can land incrementally.

## Plurals

Every count-bearing string is a plural key (`foo_one` / `foo_other` in `en`),
**even where English needs only two forms**. Russian, Ukrainian and Arabic have
plural categories English does not; a non-plural key leaves their translators
nowhere to put them, and retrofitting one means re-translating. i18next picks
the suffix from the active language's CLDR rules, so a translator adding
`count_few` / `count_many` needs no code change.

The rule runs in the other direction as well: a locale writes **its own**
categories, not English's. Chinese has one (`other`), so `zh` carries a single
`_other` key per plural family and no `_one` — a mirrored `_one` would be an
entry i18next could never select. A locale's key count is expected to differ
from `en`'s for exactly this reason; parity is per plural *family*, not per
key.
Arabic is the worst case and it already ships: **six** categories — `_zero`,
`_one`, `_two`, `_few` (n%100 = 3–10), `_many` (n%100 = 11–99), `_other`. The
38 plural families in `en` therefore carry 228 keys in `ar`, which is why the
`ar` catalogue has 1,301 leaf keys against English's 1,149. A family that is
missing a category silently falls back to English, so the count check is
"6 forms per family", not "more than 2".

## Numerals

`{{count}}` is plain i18next interpolation, not `Intl.NumberFormat` — it
renders whatever `String(n)` gives, i.e. **Western/ASCII digits in every
locale**, Arabic included. (Chromium and Node both resolve `ar` to the `latn`
numbering system anyway, so nothing would change if it went through `Intl`.)
Literal digits written into a catalogue must therefore be ASCII too, or the
same screen mixes ٣ and 3.

## Dates

Every `toLocale*` / `Intl.*` call in the renderer formats against
**`activeLocale()`** (`utils/format.ts`), which reads `i18n.resolvedLanguage`
at CALL time. A bare `[]`, `undefined` or omitted locale argument resolves to
the **host** locale — i.e. the OS's — which is the #902 bug: an Arabic UI on an
English machine rendered "Mon, Jun 7" directly beneath a translated "اليوم".
**A missing locale argument is a defect, not a default.**

`activeLocale` is a plain module function, not a hook, matching `timeAgo.ts`
and `formatFileSize`: these helpers are called from a dozen components, and
making them hooks would change a dozen signatures to fix a formatting bug. The
re-render comes free — `changeLanguage` re-renders everything subscribed
through `useTranslation`, and every call site already is.

Three components format inline rather than through a helper here (the two
invite rows and `ThreadMessageRow`); they import `activeLocale` directly. New
code should prefer an existing helper over a fresh `toLocale*` call.

## RTL

`languages.ts` carries a `dir` per language and `index.ts` writes it to
`<html dir>` on every change. `ar` ships (#855) with `dir: "rtl"`, and the
component layout follows it. These are the conventions a second RTL locale
(Hebrew, Farsi, Urdu) inherits without relearning anything.

### 1. Directional CSS is logical; screen-physical CSS is not

Anything expressing *reading order* — indentation, gutters, the edge a rule or
a rail faces, the corner a badge sits in, text alignment — is written with
logical properties, and there are now none of the physical equivalents left in
`frontend/src`:

| Instead of | Write |
|------------|-------|
| `ml-*` / `mr-*` | `ms-*` / `me-*` |
| `pl-*` / `pr-*` | `ps-*` / `pe-*` |
| `border-l` / `border-r` (and `-2`) | `border-s` / `border-e` |
| `text-left` / `text-right` | `text-start` / `text-end` |
| `absolute left-*` / `right-*` | `absolute start-*` / `end-*` |
| `paddingLeft` / `borderLeft` in a `style` or `.css` | `paddingInlineStart` / `border-inline-start` |

Flexbox and Grid need no help: a `flex-row` and a `grid-cols-[…]` already lay
out along the inline axis, so the sidebar, the composer row, the IRC message
row and the refined avatar gutter all mirror for free. Only explicitly
positioned or explicitly sided things need converting.

**The exception, and it is a real one: `left`/`right` that mean the SCREEN.**
Three places stay physical on purpose, each commented as such in the source:

- `Layout/WindowResizeEdges.css` — `.wre-w` must grab the window's physical
  west edge because that is the edge the compositor drags, and
  `ew-resize`/`nwse-resize` name physical directions too.
- `Layout/TitleBar.tsx` — its `paddingLeft`/`paddingRight` frame the OS window
  controls (macOS traffic lights top-left, Windows caption buttons top-right),
  whose positions come from the platform, not from the app's reading
  direction.
- `.vs-vol` in `voice-stage.css` pins `left` *and* `right`, so it is a
  full-width strip with no direction to follow.

Video tile corner overlays (`.vs-tl`/`.vs-tr`/`.vs-bl`/`.vs-br`) went the other
way: they are chrome laid *over* the picture — a name badge, a signal meter —
so they are anchored with `inset-inline-*` and swap sides the way Zoom and
Teams move theirs. The video frame itself is of course never mirrored.

### 2. Icons mirror only if they encode direction

Two component classes in `index.css` carry this, and nothing else should
hand-roll a `scaleX`:

- `.rtl-mirror` — for a glyph drawn for LTR that must flip under `dir=rtl`:
  back/forward chevrons and arrows, the composer's send arrow, the sidebar's
  collapse caret, the `TextInput` focus caret, reply arrows.
- `.rtl-unmirror` — for a glyph the LTR design already draws flipped (the
  terminal skin's reply arrow, the voice stage's "leave" `LogOut`): under
  `dir=rtl` it returns to its natural drawing, which is the mirrored one.

Everything else must carry **neither**. A mic, a checkmark, a trash can, a
smiley, a shield, a hash — mirroring those is the single change that makes an
RTL build look broken rather than translated. Media transport (`SkipBack` /
`SkipForward` in `ui/AudioPlayer.tsx`) is deliberately in this group: a
timeline is not a sentence, and Spotify/YouTube do not mirror theirs either.

### 3. Foreign and machine text is isolated, never inherited

A Latin name at the end of an Arabic sentence jumps to the wrong side unless it
is bidi-isolated. Two tools, and the choice between them is about *what the
string is*:

- **`<bdi>`** (first-strong auto direction + isolation) for **user-generated**
  text: message author names, `@mention` tokens, any bare `@handle` (the
  profile panel, the DM header, the incoming-call and new-message status
  alerts), sidebar group/channel/DM labels, right-panel member rows,
  breadcrumb segments, voice-tile participant names. Use the element, not a
  `<span dir="auto">` — it is the same behaviour with the intent on the tag.
  Without it `@alice` renders as `alice@`: the sigil is a neutral and drifts to
  the other end of the run.
- **`dir="auto"`** on a **block that holds a whole message body**
  (`message-content` in both skins, and reply-preview snippets), so an English
  message in an Arabic app still reads left-to-right and an Arabic message in
  an English app still reads right-to-left. This is what Slack and WhatsApp do
  per message.
- **`dir="ltr"`** for **identifiers and machine values, which are LTR in every
  locale**: URLs (`ui/LinkifiedText.tsx`), invite links, safety numbers, update
  commands, any `<code>`; **clock readings** (`message-timestamp` in both
  skins), because `6:00 AM` in an RTL paragraph reorders to `AM 6:00` — the
  characters are untouched, so only the painted positions show it; and the
  OTP/PIN digit row (`ui/InputOtp.tsx`), which is the sharp one. Left to
  inherit `rtl` the boxes reverse, so the first box you type into renders
  last: a wrong PIN every time with nothing on screen to explain it. Pinning
  the container LTR also keeps `ArrowLeft`/`ArrowRight` meaning previous/next,
  which its key handler assumes.

Note that `dir` on an element implies `unicode-bidi: isolate` per the HTML
rendering spec, so no extra CSS is needed. Note also that `<bdi>` alone often
fixes a case that `dir="ltr"` was added for — its default is `dir=auto`, so
`6:00 AM` resolves LTR on its first strong character anyway. Both are used
together where the answer must not depend on the content (a clock in a locale
that formats it differently, an all-digit identifier with no strong character
at all).

The `ar` catalogue additionally carries invisible LRM marks (U+200E) around
`:shortcode:`, `@handle` and `{{used}}/{{count}}`. Those are **inside the
translated strings** — leave them alone; they solve the case where the
interpolated value is not in its own element and so cannot be isolated by
markup.

### 4. Horizontal arrow keys resolve against the direction

`ArrowRight` is not "next", it is "rightwards". `utils/direction.ts` is the one
place that knows this: `horizontalArrowStep(key, el)` returns `+1` / `-1` /
`0`, and `ui/NavigableList.tsx`, `ui/NavigableGrid.tsx` and
`Emoji/EmojiPicker.tsx` all go through it (#902 — before that all three
hardcoded `ArrowRight: +1` and walked an Arabic user backwards).

Direction is read from the **focused element's computed style**, not from
`i18n.language` or `<html dir>`, and that is load-bearing: the app deliberately
contains LTR islands inside an RTL page. `ui/InputOtp.tsx` pins its digit row
to `dir="ltr"` and its own key handler needs ArrowLeft to keep meaning
"previous box" there. Asking the element gets that right for free; asking the
language would break it.

Vertical arrows need none of this — `dir` mirrors the inline axis only, and the
block axis is top-to-bottom everywhere.

### 5. Still LTR-assuming

Known and deliberately not fixed:

- **`.sidebar-item` / `.sidebar-item-active` in `index.css`** were converted
  along with everything else, but they are currently **dead** — no component
  references either class.
- **Arabic copy runs materially longer** than the English abbreviations it
  replaces (`5m` → `5 دقائق`), so tight trailing-metadata slots can wrap. That
  is a sizing problem, not a direction problem, and is unaddressed.

## Wire values are copy the moment they reach the screen

A backend enum that happens to read as an English word is the easiest i18n bug
to ship, because nothing looks wrong in English. `admin`, `member`, `excellent`,
`strict` are protocol tokens; rendering one — or interpolating it into an
otherwise translated sentence — leaves a French user reading
"Connexion : excellent". Map the token to keys instead.

Write the mapping as **literal `t("…")` calls**, one per value, rather than
building the key from the value with a template literal:
`scripts/i18n-check.mjs` resolves literal call sites only, so a computed key is
invisible to it and a typo survives to production. Keep a fallback to the raw
value for a token the client does not know — a blank slot is worse.

## Keyboard glyphs: words are copy, symbols are not

`keyboard/keyCombo.ts` splits its labels in two.

**Translated** (`common:keys.*`): the key names that are *words* — Ctrl, Alt,
Shift, Esc, Space, Enter, Tab, Backspace, Delete, Home, End, Page Up/Down. A
German keyboard is labelled *Strg* and *Umschalt*, and "Esc" is an abbreviation
of an English word.

**Never translated:** the glyphs. `⌘ ⌥ ⇧` (Apple ships these untranslated in
every macOS localization), the arrows `↑ ↓ ← →`, and the backtick. They are
symbols engraved on the physical key, identical in every locale, and
translating one only gives six locales a chance to get it wrong. The arrows are
also **not** mirrored under RTL: they name a key you press, not a direction you
read.

## Casing translated copy

**Never `.toUpperCase()` / `.toLowerCase()` on a string that has been through
`t()`.** The bare methods apply the locale-INVARIANT mapping, which is a
different answer from the language's own: Turkish uppercases "i" to "İ" and
"ı" to "I", so an invariant upcase spells a different letter rather than merely
an odd-looking one. In the caseless scripts already shipped — Arabic, Chinese —
the call is a no-op wearing the costume of a transform.

Prefer letting the catalogue supply the intended form: it is the only layer
that knows, and it is free in scripts that have no case. Where a skin's
typography wants a cased variant of a string the catalogue already carries —
the terminal skin's `[ACTIVE]` invite badge is the live example (#911) — use
`localeUpperCase(value, activeLocale())` from `i18n/languages.ts`, which is the
only sanctioned spelling and the seam `frontend/tests/locale-casing.test.ts`
pins. Casing an ASCII identifier (a slug, a file extension, a wire value) is
not this and needs none of it.

## Not translated

Console output, `Error` values destined for logs, `data-testid` values,
developer-facing/debug strings, and protocol or preference key names.

Server-authored human-readable strings (`detail` on an account-key audit or a
build verification, voice/screenshare error text) also arrive in English and
are rendered verbatim. Translating them would mean moving the copy into the
catalogue and sending a code instead — worth doing, not done, and not a
renderer-side fix.

## Tests

`e2e/i18n.spec.ts` (browser tier, both skins) covers: the selector renders and
persists across reload; switching language changes rendered copy; and a key
missing from a non-English catalogue falls back to English rather than
rendering the raw key. It seeds a synthetic test locale through the same
`__POLLIS_PRELOAD__` mock the other specs use, so the assertions do not depend
on which real locales happen to ship.

#902 added three groups to it: dates (drives the real `ar` locale with the
BROWSER locale pinned to `en-US` via `test.use({ locale })`, because the bug
only exists where the two disagree, and asserts on Arabic SCRIPT rather than on
a specific weekday string, which is CLDR's business and moves between ICU
versions); keyboard key names; and member roles. The last two use synthetic
catalogues for a sharp reason — the English copy for `channels:members.role.member`
is deliberately the same word as the wire value it replaces, so under any real
locale the fallback would render an identical string and the test would pass on
unfixed code.

`e2e/rtl.spec.ts` (browser tier, both skins) covers the layout half, and does
it by **measuring geometry** — `getBoundingClientRect`, a `Range` over a text
node, or the resolved *physical* border width the browser actually painted.
Nothing in it asserts on `dir`, on a class name, or on a utility: `<html dir>`
was already correct before any of the mirroring work existed, so an
attribute-shaped test passes on entirely unmirrored code. That is the specific
trap this file is written against. It drives the real `ar` locale (not a
synthetic one — `dir` comes from the registry) and pins the LTR case in the
same test body, because a one-sided assertion is also satisfied by a layout
that is broken in both directions.

Its arrow-key group (#902) follows the same rule: it presses a key and asserts
that focus moved further RIGHT ON SCREEN, which is one statement true in both
directions, instead of asserting an index — an index-shaped test has to encode
the answer it is checking and passes on unfixed code in LTR.

`frontend/tests/locale-casing.test.ts` (same runner) covers `localeUpperCase`,
and is the reason the unit tier is now part of `frontend-check.yml` rather than
something you had to remember to run. The bug it pins (#911) is invisible in
every locale that ships — none of them cases differently from the invariant
mapping — so there is no browser assertion that could fail on the unfixed code.
A unit test over the helper can ask the question today.

`frontend/tests/direction.test.ts` (Node's built-in runner, `pnpm --filter
frontend test`) covers `arrowStep` directly. That is where `NavigableGrid`'s
half of the arrow-key fix is proven: it renders only inside the voice stage,
which needs a live LiveKit session the browser tier does not have, so the
shared helper is the only reachable seam.

`node scripts/i18n-check.mjs` is the catalogue integrity gate and runs
independently of either spec. **Untranslated is a warning; wrong is a
failure.** A key present in `en` and absent from a machine-translated locale
renders English via `fallbackLng` — visibly behind, never broken — so it is
reported with a per-locale count and the run still passes. That is the normal
steady state: a feature lands in English and the translation pass follows,
and failing the build for it would force every feature PR to either block on
translation or invent six machine translations nobody reviewed. The same
applies to a plural family a locale has not started at all.

Everything indicating the catalogue is WRONG rather than merely BEHIND stays a
hard failure: a key the locale has that `en` does not (dead weight from a
rename); a plural family the locale has *started* but left incomplete (the
copied-from-English bug the script exists for); placeholder drift, including
the rule that a form covering more than one number must show `{{count}}`; an
empty string, which renders as a blank slot instead of falling back; and a
call site with no `en` entry, which renders a raw key id.
