# Bots (#1182)

A bot is a **user** (`users.kind = 'bot'`) scoped to **one group** for its whole life; its **hosts are its devices** (`user_device` rows under the bot, each with its own cert, leaf and key-package pool). Epic and settled design: #872. Schema: `pollis-schema/migrations/000052_bots.sql` (see [Database](./database.md)). DS: `pollis-delivery/src/bots.rs`. Wire types: `pollis-api/src/bots.rs`.

This article is the internal layer. User and developer docs (admin guide, self-hosting, alerts webhook, job-loop concepts) are in [`docs/bots/`](../../docs/bots/README.md), mirrored on the website as `website/bots*.html`; update them alongside behaviour changes.

## What the schema refuses
Triggers, so no DS code is in the path (tests: `pollis-delivery/tests/bot_schema.rs`): a bot user without its `bot` row, its membership or its exact address `bot-<id lowercased>@bot.invalid`; a human with a bot row or any `bot.invalid` address; `kind` changing; a bot in another group, as admin, as group owner, in a DM, invited, asking to join, or holding a push token; a bot's membership or `bot` row deleted while the bot exists; a group deleted while it has bots; a trigger claim for a non-bot.

**Order.** Create: `bot` → `group_member` → `users` → `user_device`. Delete: `users` → `bot` → everything else (`bots::delete_bot_in_tx`, used by `/v1/bots/delete`, a bot's own `/v1/account/delete`, and `teardown::purge_group`). Nothing relies on foreign keys being off: the create transaction sets `PRAGMA defer_foreign_keys = ON` (the membership names its user before that row exists), and the membership's delete guard keys on the bot *user*, so a cascade from deleting the user is allowed; `tests/bots.rs` runs create, delete and teardown with foreign keys enforced.

## DS endpoints
| Path | Auth | Purpose |
|---|---|---|
| `/v1/bots/pairing/request` | none, `probe` tier, 10 000 open max | Host files a request (ephemeral X25519 key, code lookup hash, poll verifier, device id; `NewBot{account_id_pub}` or `ExistingBot{bot_user_id}`); TTL 10 min |
| `/v1/bots/pairing/lookup` | device-signed, admin of `group_id`, `probe` tier | Find an open request by the typed code's hash; an add-host request only through its bot's group. The client re-derives the code from the returned ephemeral key |
| `/v1/bots/pairing/status` | poll secret | Host awaits `pending` / `created{bot_user_id, group_id}` / `wrapped{…, wrapped_account_key}`; unknown, expired, wrong secret all 401 |
| `/v1/bots/create` | device-signed admin | One transaction: bot row, membership, user (key into `account_key_log`), host device (no cert yet), security events on admin and bot. Cap `MAX_BOTS_PER_GROUP` = 25 → `limit_reached` |
| `/v1/read/bots` | device-signed admin | Bots of a group with hosts (`certified`, `revoked_at`) and the limit |
| `/v1/bots/delete` | device-signed admin | Account deletion of the bot, then leave wake-ups and the owed commit-log purge |
| `/v1/bots/hosts/approve` | device-signed current admin of the bot's group | Store the admin's signed host approval (opaque to the DS) on the bot's open add-host request; inbox nudge `bot_host_approval` |
| `/v1/bots/hosts/pending` | device-signed bot host | Approved, unwrapped add-host requests for the signer's bot |
| `/v1/bots/hosts/wrap` | device-signed bot host | First wrap wins (status CAS); approver re-checked as a current admin; registers the new host's `user_device` row; nudges the group's admins' inboxes with `bots_changed {group_id}` (DS-only, content-free) so an open Bots page re-reads |
| `/v1/bots/triggers/claim` | device-signed bot host, own installation | `(installation_id, trigger_key)` PK: first claim wins, the winner's retry wins again; kept 7 days |
| `/v1/bots/app-state/read` | device-signed bot host, own installation | #2004: sealed App state entries by 32-byte key id, plus the installation's usage (sealed bytes, rows) |
| `/v1/bots/app-state/commit` | device-signed bot host that won the claim on `trigger_key` | #2004: a job's writes, all or none, each at the version the host read (`conflict` otherwise), once per claim (`bot_trigger_claim.state_committed`; a retry answers `already_committed`), within `BOT_APP_STATE_MAX_BYTES` = 1 MiB per installation (`over_quota`) |

After `created`/`wrapped` the host publishes its cert through `/v1/auth/publish-device-cert` (cert-validity gate, `user_id` in the body) and then its key packages, device-signed.

Removing a host is `/v1/devices/revoke` with `user_id` = the bot: allowed to any current admin of its group (`account::revoke_owner`), security event on both.

## DS refusals for a bot (tests: `pollis-delivery/tests/bots.rs`)
No OTP issued or verified for a `bot.invalid` address; no email change (403 for a bot, silently nothing to a `bot.invalid` target); no directory hit by username or email (`user_by_identifier` matches `kind = 'human'`); no DM create/add either direction; no group create; no invite, invite redemption or join request; no admin role, removal or leave (only deletion); no push token; no device link create/accept; no identity rotation or reset; key-package claims on a bot only by admins of its group. Reads never return a bot's email. `GroupMemberWire` and `UserWire` carry `is_bot` for the Bot badge (default false for older DSes).

## Teardown
A group left with no people (leave, or the last person's account deletion) is torn down with its bots; ownership and admin handoff never pick a bot. Account deletion of an admin blanks `bot.created_by`.

## Client (`pollis-core/src/commands/bots/`)
API summary at the top of `mod.rs`. One `AppState` per installation, with its own keystore and data dir (`AppState::local_dir`, no longer harness-only), so installations in one process share nothing.

**Pairing code** (`code.rs`): eight characters, the enrollment SAS alphabet and input rule, HKDF over the request's ephemeral key, the host's device id and the target (the new bot's account key, or the existing bot's id), so a DS that swaps any of them breaks the admin's typed code. `code_lookup` = SHA-256 of a domain and the normalized code. Unsalted by request id (the admin finds the request by the code).

**Host** (`host.rs`): `start_new_bot_pairing` generates the account seed and device id locally; `await_pairing` backs off 1→8 s to the TTL (one call, like `await_enrollment_approval`), then opens the store, publishes the cert (cert-validity gate) and key packages, checks through a signed read that the DS holds the account key this host generated (else "tampering"), confirms `is_bot`, and saves the installation. An add-host pairing unwraps the account key with the enrollment unwrap (`device_enrollment::unwrap_account_key`). `join_bot_group` drains Welcomes, then external-joins: a new bot's first host waits (bounded) for the Welcome the admin's reconcile sends; another host of an existing bot is sent none, so it external-joins at once, as a person's new device does.

**Host approval** (`approval.rs`): canonical JSON (sorted fields, compact, no unknown fields, re-serialization must match), ML-DSA-44 by the admin's device over `pollis-bot-host-approval-v1 ‖ 0x00 ‖ payload`, wrapped as `{payload, signature}` base64. `handle_host_approvals` verifies each pending request from the host's own state (`verify_host_approval`): approver device is a leaf in the host's local tree of the group, `Certified` under the approver's account key (`IdentityDirectory`, TOFU-pinned), signature under that leaf key, own bot and group, unexpired with a lifetime ≤ 10 min, request id not in the local `bot_consumed_host_request` table, approved ephemeral key byte-equal to the request's (else `Tampered`), the transparency log not `Alarm`, and the roster read listing the approver as admin (re-read just before the wrap). Wrapper rule (no host is assumed awake): hosts that are certified and seen within 15 min, sorted by device id; rank *k* wraps at `issued_at + 30·k s`, capped 30 s before the approval expires (`Deferred` until then). A peer not seen for 15 min is not waited for; a host that will not be up at its `retry_at` (a one-pass `run --once`) uses `WrapTiming::Now` and wraps at once. The DS's status CAS makes the first wrap win and the rest record the request consumed. The wrap is `device_enrollment::wrap_account_seed_to`, the one human enrollment uses.

**Unattended start** (`unattended.rs`): per-bot keystore slot `bot_installation_<id>` (account seed, local-DB key, device id, group), written only by pairing. `start_unattended` refuses (`unattended_refused: …`) an account with a PIN, an account without a slot, and one the DS does not report as a bot.

Flows: `src-tauri/tests/flows/bots.rs` (harness: `BotHostClient`, `pair_new_bot`, `plant_host_approval`, `swap_pairing_ephemeral`).

## Runtime
`pollis-bot` (crate `pollis-bot/`, install/run: `pollis-bot/README.md`) hosts bot installations and runs their **job loop**. Headless, on `pollis-core`, dials out to the DS only, survives restarts (installations reopen unattended from their keystore slot; the first job after start catches up on everything missed).

**Installations.** One runtime hosts many (several bots, several groups). Each has its record `<data dir>/installations/<id>/installation.json`, its own encrypted store `<data dir>/stores/<device id>/` (named by the host's device id, which is fixed when the pairing request is filed, before the bot's id is known), its own keystore slot and its own `AppState` (`core_host.rs`); nothing is shared. `main.rs` relocates the core's data dir (`set_data_dir_override`) to the runtime's data dir, so where there is no OS keychain the keystore file is `<data dir>/keystore.pks`, never the `pollis` app's (the file store has no cross-process lock). The installation id is the bot's user id while a bot has one installation. Limit: `max_installations` in `<data dir>/config.json`, **default 8**; `run` refuses to start past it and `pair`/`add-host` refuse to add past it (`installations::check_capacity`).

**Job loop** (`pollis-bot/src/job.rs`, one per installation):
1. Trigger: a wake-up (realtime new-message / membership / reconnect event for the group, or the start of the runtime) or a webhook call. Never a timer.
2. Take the installation's lock (`Installation::run_job`; one job at a time per installation, installations run in parallel). Wake-ups that arrive before a queued job starts catching up fold into it.
3. Unseal the installation (`InstallationCore::open`: `bots::start_unattended` on a fresh `AppState`, then a flush of any post an earlier job could not finish) and catch MLS up through the normal ingest path (`InstallationCore::catch_up`); messages newer than the stored cursor become message triggers, oldest first. The bot's own messages are never triggers.
4. The installation's `Handler` returns `Action`s (`Handler::handle_job` → `HandlerOutput { actions, state }`): the built-in alerts handler, or a sandboxed **App** (#2004, below), which also returns App state writes at the versions it read.
5. A trigger with actions or state writes is claimed on the DS (`/v1/bots/triggers/claim`, `(installation_id, trigger_key)`); a lost claim discards the actions. A won claim then commits the App's state writes (`/v1/bots/app-state/commit`); a conflict (another host moved a key since this job read it) re-runs step 4 on the new state, up to `STATE_CONFLICT_ATTEMPTS` = 3, then the trigger ends `handler_failed` with nothing applied. Trigger keys: `msg:<envelope id>`, `hook:<delivery id>` (later `req:<request id>`, `slot:<slot time>`); the kind prefix keeps a sender-chosen delivery id from posing as an envelope id.
6. Each action is checked against the grants (hard-coded in #1182: `post` to a text channel of the bot's own group, by id or name) and applied through the normal durable send path. Refused actions are reported, never applied; a handler error discards every action and claims nothing.
7. Seal the installation (`bots::stop_unattended`, on every path) and release the lock.

Nothing is held open between jobs and nothing assumes a host stayed up: "unseal → catch up → run → seal" is the only way work happens (measured in the flows harness: about 4–5 ms per job to open and close, plus one DS round trip for the is-bot check against a real DS). An `Approvals { wrap_now }` job checks pending add-host approvals and then catches up; it runs at start, on the `bot_host_approval` nudge or a reconnect, and once at a deferred request's `retry_at`. `run --once` is a one-pass run for a host that is started, works and exits: every installation runs an approvals job with `wrap_now` (it will not be up at a later `retry_at`), then the process exits sealed.

A message's cursor advances once its outcome is final (posted, claimed elsewhere, refused, handler failed). A transient failure (claim or send unreachable) stops the job at that message without advancing, so the next wake-up retries it in order. Posted message ids are derived from `(installation, trigger key, action index)` (`job::action_message_id`), so a retry re-sends the same message rather than a second one, and the winner's repeated claim answers `won` again.

**Wake-ups** (`core_host.rs`, feature `realtime`, on by default) are a separate adapter (`BotHost::watch`) that only calls `Runtime::wake` / `Runtime::approvals`; it never runs a job or touches a job's state. It holds its own signed-in `AppState` (its rooms re-mint LiveKit tokens with the device's signature) with `LiveKitState::wake_only` set, so it never applies a membership wake to MLS state: that happens inside a job. It joins the group's room and `inbox-<bot id>`; message, membership and roster events wake the loop, `bot_host_approval` and a reconnect run an approvals job. It enables pollis-core's `realtime` feature: the LiveKit data rooms without the audio stack (`media` is a superset of it, so desktop is unchanged and mobile enables neither); libwebrtc is still linked, since receiving LiveKit data needs a WebRTC peer connection. Without it (or under `--once`) the runtime catches up when a job runs. Read cursors are rows of `bot_trigger_cursor` in the installation's encrypted store (`bots::trigger_cursor` / `set_trigger_cursor`); a channel seen for the first time starts at its newest message, so history is never replayed as triggers.

**Alerts webhook** (`webhook.rs`). Off until configured (`config.json` `"webhook": {}` or `run --webhook [ADDR]`); binds `127.0.0.1:8787` unless told otherwise. `POST /hooks/<installation_id>` with `{"channel", "text"}`, authenticated by `Authorization: Bearer <secret>` or `X-Pollis-Signature: sha256=<hex HMAC-SHA256(secret, body)>` (a present signature must verify; a bearer cannot rescue it). The per-installation secret (`pbw_…`) is generated on the first start with the webhook on, kept in the installation's keystore slot, printed once; `pollis-bot rotate-secret` replaces it. Optional `X-Pollis-Delivery` names the delivery: send the same one to every host of a bot and exactly one posts. Order of checks: unknown installation 404, bad auth 401, **rate limit 429 + `Retry-After` (per installation: burst 10, refilled at 30 a minute; `webhook.burst`/`webhook.per_minute`)**, malformed 400. Answers: `posted` 200, `claimed_elsewhere` 200, `refused` 422, `failed` 5xx with a fix, `accepted` 202 if the job takes over 30 s (it still finishes). Body cap 64 KiB; `post` text cap 4000 characters. `pollis-bot post` signs and sends to this same endpoint.

**Forget.** `pollis-bot forget --installation <id>` removes an installation from the host (record, store, keystore slots via `bots::forget_installation`, webhook secret) after an admin revoked the host or deleted the bot; the open-failure fix points at it.

**State and logs.** Every line is scoped to the runtime or one installation; every failure ends with one fix (`JobError::fix`). States: pairing → waiting for approval → joining → (run) starting → catching up → connected, or job failed with the error and fix. `run` writes `<data dir>/status.json` on every state change (not on a timer); `pollis-bot status` reads it.

**Apps** (`pollis-bot/src/app_handler.rs`, #2004). `HandlerKind::App { component, manifest }` in `installation.json` runs a WebAssembly component through `pollis-app-host` (sandbox, WIT `pollis-app-wit/wit/app.wit`, enforcement and its tests: see `docs/bots-threat-model.md`). Per trigger: the trigger maps to the App's (message, or webhook with body `{"channel","text"}`); the App runs in a fresh sandbox on a blocking thread (`spawn_blocking`) with `AppServices` as its host services; its actions become `Action::{Post, Reply, React, EditOwn, DeleteOwn}` (the loop checks each channel again against the group's text channels, `Refusal::NotInGroup`); a trigger the App's grants exclude is `NoActions` (`JobError::NotDelivered`), a trap/timeout/error is `HandlerFailed`. Services: App state through the open installation (`InstallationCore::state_read` / `state_commit`); `http-fetch` through `PublicHttpClient` (public addresses only, connects to the address it checked, no redirects or proxy); `query-messages` returns the trigger's message until the message log (#2008); `log` and the App's stdout/stderr go to the runtime log (`app <level>: …`). The compiled component is cached per process by App hash. Grants: until approvals (#2005), a debug build reads them from `POLLIS_APP_DEV_GRANTS`; a release build refuses to load an App.

**App triggers.** Messages carry the author's username and is-bot from the group roster (`InstallationCore::members`, one DS read per App trigger). A message naming the bot by `@username` (`bots::mentions_username`, the #843 rule; `@all` excluded) goes to `on-mention` when the effective grants include `mentions`, else to `on-message` (one delivery per message). Webhooks: an App installation's listener entry is `raw` (`HookEntry::raw`), so `on-webhook` gets `WebhookPayload::Raw { body, content_type, headers }` (headers: `user-agent` and `x-*` minus the signature; never `authorization` or cookies). Schedules: manifest `schedules: [{name, every 60..604800 s, offset < every}]`, slots at `k·every + offset` UTC; trigger key `slot:<name>@<unix s>`; per-host cursor in the encrypted store (`bot_trigger_cursor` row `schedule:<name>`, `bots::schedule_cursor`); first sight seeds at the current slot; each job runs up to `MAX_MISSED_SLOTS` = 3 newest due slots per schedule (older counted in `JobReport::skipped_slots` and logged); `Runtime::arm` sets one timer per installation to the next slot after every job (no polling). Commands (#2018) and requests (#2008) are not delivered yet; the sandbox covers their exports.

**`app install`** (`app::app_install`, debug builds only; release refuses): validates the artifact dir (`pollis-app.json` + exactly one `.wasm`) by loading it as `run` would, copies both to `<installation dir>/app/`, sets `HandlerKind::App`. Compiled components are cached in `<data dir>/app-cache/` (`pollis-app-host` `HostConfig::compiled_cache_dir`; entry keyed by App hash + component digest + engine fingerprint, checksummed, recompiled on any mismatch; optional). wasmtime `parallel-compilation` is on: a 12 MB ComponentizeJS App compiles in ~0.6 s on 32 cores (8.8 s single-threaded) and loads from the cache in ~30 ms.

**App state** (`pollis-core/src/commands/bots/app_state.rs`, migration `000053_bot_app_state.sql`). One store per installation on the DS, shared by all its hosts. Keys are derived per installation from the bot's account secret (every host holds it): `key_id = HMAC-SHA256(mac_key, key)`, value `= nonce ‖ ChaCha20-Poly1305(seal_key, len(key) ‖ key ‖ value)` with the installation id and key id as associated data. The DS sees ciphertext, sizes, versions and write times only. Writes are optimistic (`expected_version`, 0 = absent) and committed only under a claim this device won, once. The manifest's `state.quota` is enforced by the sandbox on plaintext (key + value bytes; usage = sealed bytes − 30 per row); the DS caps 1 MiB sealed per installation and 70 000 bytes per entry (schema triggers). Deleted with the bot.

**Tests.** `cargo test -p pollis-bot`: the loop over a fake core with a shared fake DS (`tests/job_loop.rs`: lock exclusivity, handler-error discard, grant refusal, claim lost, two hosts one post, retry without skipping), the webhook (`webhook.rs` unit tests: bad secret, bad HMAC, unknown installation, rate limit, malformed), the runtime and subcommands end to end over a fake host (`tests/runtime.rs`, `tests/app.rs`), the binary's command line (`tests/cli_args.rs`). App handler over the fake core (`tests/app_handler.rs`: the fixture App through the loop with two hosts sharing state, an ungranted trigger runs nothing, a trap applies nothing, a state conflict re-runs the handler). DS: `pollis-delivery/tests/bots.rs` (App state under a won claim only and once, no clobbering, quota, auth, deleted with the bot), `bot_schema.rs`. Flows (`src-tauri/tests/flows/bot_runtime.rs`, hosts sealed between jobs): an App on two asleep hosts shares its sealed state and answers once, beside an unchanged alerts bot; two real hosts of one bot post exactly one reply; the only host, asleep and unseen, wakes on the nudge and wraps; an asleep first-ranked peer delays a wrap by a bounded stagger (and not at all once unseen for 15 min or under `wrap_now`).
